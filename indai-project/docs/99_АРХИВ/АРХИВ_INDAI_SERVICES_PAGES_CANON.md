## 0. Роль документа в системе

Данный документ фиксирует **каноническую архитектуру страниц услуг INDAI** и переводит её в проверяемые правила реализации.

Документ отвечает на вопросы:

> Какие страницы услуг существуют?  
> Из чего состоит каждая страница?  
> Как проверить, что страница реализована корректно?

Документ обязателен к соблюдению при разработке сайта, написании контента, работе дизайнеров, QA-приёмке и использовании AI-агентов.

## 2. Пользователь Service Page

### 2.1 Основной сценарий входа

Пользователь Service Page — это тот же целевой пользователь, определённый в `HOME_PAGE_IMPLEMENTATION_RULES §2.1`, **после прохождения фильтрации** на Home Page.

Он уже понимает:
- INDAI работает с промышленными объектами
- это инженерный процесс, а не бытовая услуга
- для начала работы потребуются данные об объекте

**Следствие:** Service Page НЕ повторяет фильтрацию. Она начинает с сути.

### 2.2 Прямой трафик (поиск, ссылка, закладка)

Пользователь может попасть на Service Page напрямую, минуя HomePage.

**Требование:** Service Page должна быть самодостаточной — не зависеть от предварительного просмотра HomePage. Блок 1 (Ориентация) выполняет роль минимальной рамки.

### 2.3 Нецелевой пользователь на Service Page

Если нецелевой пользователь попал на Service Page напрямую:
- инженерный язык и контекст страницы выполняют функцию пассивной фильтрации
- явных «вы не наш клиент» сообщений не требуется
- AI-ассистент (если присутствует) может корректно перенаправить

## 3. Функция Service Page (строго)

Service Page **объясняет**, а не продаёт.

Её единственные функции:

1. **Показать суть решения** — какой класс задач решает эта услуга.
2. **Описать инженерный подход** — как INDAI подходит к задаче (не что использует).
3. **Обозначить область применения** — типы объектов и контексты.
4. **Подготовить к инженерному диалогу** — следующий шаг = описание объекта, не покупка.

**Диагностический тест:**  
Если после прочтения Service Page пользователь думает «хочу заказать» — функция нарушена.  
Если думает «хочу обсудить, подходит ли это для моего объекта» — функция выполнена.

## 4. Перечень канонических услуг

### 4.1 Каноническая карта услуг

Следующие страницы услуг **ДОЛЖНЫ** существовать на сайте INDAI.

| # | Slug | Название | Класс задачи |
|---|---|---|---|
| 1 | `/services/industrial-cleaning` | Промышленная очистка | Удаление отложений, восстановление проходимости и теплообмена промышленного оборудования |
| 2 | `/services/surface-preparation` | Подготовка поверхностей | Подготовка металлических и бетонных поверхностей к нанесению покрытий, ремонту, инспекции |

- Добавление новой страницы = addendum к данному документу

## 5. Канонический шаблон страницы услуги

Каждая страница услуги **ОБЯЗАНА** следовать нижеописанному порядку блоков. Менять порядок, удалять или добавлять блоки без addendum **запрещено**.

### Блок 1 — Ориентация

**Функция:** Объяснить, какой класс задач решает данная услуга.

| Разрешено | Запрещено |
|---|---|
| Название класса задачи | Название метода или технологии как заголовок |
| Описание проблемы, которую решает услуга | Описание оборудования или бренда |
| Класс результата: «восстановление параметров», «подготовка к ремонту» | Конкретный результат: «повысим КПД на 35%» |
| Указание, что решение инженерное | Слова «быстро», «дёшево», «гарантия» |

**Эталонный пример (допустимо):**
> «Промышленная очистка — восстановление рабочих параметров оборудования, подверженного образованию отложений, накипи и коррозионных продуктов.»

**Эталонный пример (запрещено):**
> «Мы быстро и качественно очистим ваше оборудование. Гарантия результата.»

---

### Блок 2 — Проблемы бизнеса

**Функция:** Показать, какие бизнес-проблемы являются входной точкой для данной услуги.

| Разрешено | Запрещено |
|---|---|
| Проблемы и боли: снижение теплообмена, рост энергозатрат, внеплановый простой | Описание услуг INDAI |
| Формулировки от лица контекста клиента | Формулировки «мы решаем», «мы гарантируем» |
| Связь проблемы с эксплуатационным контекстом | Абстрактные утверждения без привязки к реальности |

---

### Блок 3 — Объекты и области применения

**Функция:** Показать типы оборудования / объектов, к которым применима данная услуга.

| Разрешено | Запрещено |
|---|---|
| Перечисление типов объектов: теплообменники, котлы, трубопроводы, резервуары | Создание подстраниц под каждый тип объекта |
| Группировка по классам оборудования | Группировка по отраслям |
| Указание контекста: «объекты энергетического комплекса» | Отраслевые лендинги: «очистка для нефтегаза» |

---

### Блок 4 — Инженерный подход

**Функция:** Показать принцип, по которому INDAI подходит к задаче. НЕ описание технологий.

| Разрешено | Запрещено |
|---|---|
| Логика: обследование → диагностика → подбор метода → выполнение → верификация | Перечисление оборудования и брендов |
| «Метод подбирается под параметры объекта» | «Мы используем Kärcher HDS 1000» |
| Принцип валидации результата | Обещание конкретного результата |

**Эталонный пример (допустимо):**
> «Выбор метода определяется характером отложений, материалом оборудования и эксплуатационными ограничениями объекта.»

**Эталонный пример (запрещено):**
> «Мы используем технологию гидродинамической очистки давлением до 1500 бар, что гарантирует 100% результат.»

---

### Блок 5 — Эффект для бизнеса

**Функция:** Показать категории эффектов, а не обещать конкретные результаты.

| Допустимо | Запрещено |
|---|---|
| Категории: восстановление теплообмена, снижение аварийности, продление межремонтного интервала | Цифры: «экономия 40%», «рост КПД на 15%» |
| Классы эффектов без количественной оценки | Обещания: «гарантируем снижение затрат» |
| Контекст: «актуально при подготовке к плановому ремонту» | Универсальные маркетинговые claims |

**Разграничение факт / обещание (эталонные примеры):**

| Формулировка | Тип | Допустимость |
|---|---|---|
| «Результат — восстановление проектных параметров теплообмена» | Класс эффекта | ✅ Допустимо |
| «Повысим теплообмен на 35%» | Обещание | ❌ Запрещено |
| «Снижение риска внепланового простоя» | Категория эффекта | ✅ Допустимо |
| «Гарантируем отсутствие простоев» | Обещание | ❌ Запрещено |
| «Продление ресурса оборудования» | Класс эффекта | ✅ Допустимо |
| «Продлим срок службы на 5 лет» | Обещание | ❌ Запрещено |

| Разрешено | Запрещено |

## 6. Жёсткие запреты

### 6.1 Запрещено превращать методы в услуги

Методы (гидродинамика, крио-бластинг, пар, химическая промывка) — это **инструменты**, не продукты. Они допустимы **только внутри страницы** как часть описания подхода.

**Тест:** если URL содержит название метода (`/services/hydrodynamic-cleaning`) — архитектура нарушена.

### 6.2 Запрещено делать страницы под объекты

Объекты (теплообменники, трубы, котлы, резервуары) — это **примеры применения**. Они перечисляются в Блоке 3, но не становятся отдельными страницами.

**Тест:** если URL содержит название объекта (`/services/heat-exchanger-cleaning`) — архитектура нарушена.

### 6.3 Запрещено делать отраслевые страницы

Отрасли (нефтегаз, энергетика, ЖКХ, пищевая промышленность) упоминаются **только как контекст** в Блоках 3 и 6.

**Тест:** если URL содержит название отрасли (`/services/oil-gas`) — архитектура нарушена.

### 6.4 Запрещено дробить услуги ради SEO

- Клонирование страниц с заменой ключевых слов
- Разные формулировки одной и той же услуги
- SEO как источник архитектурных решений

> **Принцип: SEO подчиняется архитектуре, а не наоборот.**

### 6.5 Запрещено начинать страницу с технологий

Блок 1 (Ориентация) начинается с задачи клиента. Оборудование, давление, бренды, сертификаты — НЕ являются точкой входа.

### 6.6 Запрещено продавать и обещать

- «Гарантируем»
- «Лучшие»
- «100% результат»
- «№1 в отрасли»
- Маркетинговые заявления любого рода

### 6.7 Запрещено смешивать классы услуг

Каждый класс задач — отдельная страница. Инженерная очистка, подготовка поверхностей и дегазация НЕ смешиваются на одной странице.

### 6.8 Запрещено использовать лексику бытового клининга

- «Моем», «убираем», «чистим как следует»
- «Наведём порядок», «блеск и чистота»

Допустима только инженерная формулировка задач.

**Тест:** если формулировку можно разместить на сайте клининговой компании без изменений — она запрещена для INDAI.

### 6.9 Запрещено нарушать шаблон страницы

Менять порядок блоков, удалять обязательные блоки, добавлять произвольные секции — только через addendum.

### 6.10 Запрещено размещать ценовую информацию

- «От X руб.»
- Диапазоны цен
- «Бесплатный выезд / оценка / консультация»
- Калькуляторы стоимости

Ценообразование — результат инженерной валидации, не контент страницы.

### 6.11 Запрещено размещать social proof

- Отзывы клиентов
- Логотипы партнёров/клиентов
- Рейтинги
- «Нам доверяют X компаний»
- Бейджи и награды

> Social proof — инструмент убеждения. Service Page объясняет, а не убеждает.

**Исключение:** если в будущем будет создана отдельная секция кейсов (Case Studies) как самостоятельный раздел сайта, ссылки на неё из Service Page допустимы через addendum.

## 7. SEO на Service Pages

### 7.1 Принцип

В отличие от Home Page (где SEO запрещён), Service Pages **являются** точками поисковой видимости.

Однако SEO **подчиняется архитектуре**, а не наоборот (§6.4).

### 7.2 Допустимо

| Элемент | Условие |
|---|---|
| `<title>` и `<meta description>` | Формулировка описывает класс задачи, не содержит маркетинговых claims |
| Семантическая HTML-разметка (h1–h3, section) | Отражает реальную структуру блоков шаблона |
| Schema.org: `Service`, `Organization` | Без `AggregateRating`, `Offer`, `Product` |
| Open Graph / Twitter Card | Для корректного шеринга |
| Canonical URL | Стандартная техническая мера |
| Alt-теги для изображений | Описание содержимого, не keyword stuffing |

### 7.3 Запрещено

| Элемент | Причина |
|---|---|
| SEO-текстовые блоки («простыни» вне шаблона) | Нарушают структуру шаблона (§6.9) |
| Keyword stuffing в H1/H2 | Превращает инженерное описание в SEO-конструкцию |
| Дублирование страниц под ключевые запросы | Прямое нарушение §6.4 |
| Блоки «Очистка [объект] в [город]» | Геоспам, нарушает §6.2 и §6.3 |
| Скрытый текст для индексации | Манипуляция, противоречит инженерной прозрачности |
| Schema.org: `AggregateRating`, `Offer`, `Product` | Service Page — не товарная страница |

### 7.4 Принцип разграничения

> **Если SEO-элемент требует нарушения шаблона или запретов §6 — он запрещён.**

## 8. Медиа и визуалы

### 8.1 Допустимо

| Тип | Условие |
|---|---|
| Фотографии промышленных объектов | Реальные объекты, не стоковые |
| Схемы инженерного процесса | Нейтральные, без маркетинговых элементов |
| Инфографика структуры подхода | Соответствует Блоку 4, без цифр результата |
| Фотографии оборудования в контексте работы | Без брендов крупным планом |

### 8.2 Запрещено

| Тип | Причина |
|---|---|
| Фото «до / после» | Маркетинговый приём убеждения |
| Стоковые фото улыбающихся людей | Не соответствуют инженерному тону |
| Видео-отзывы | Social proof (§6.11) |
| Изображения с текстовыми overlay «Скидка», «Акция», «Хит» | Маркетинг |
| Логотипы клиентов/партнёров | Social proof (§6.11) |

### 8.3 Принцип

> **Если изображение можно разместить на сайте бытового клининга без изменений — оно запрещено для INDAI.**

## 9. AI-ассистент на Service Pages

### 9.1 Роль

На Service Page AI-ассистент — **инструмент углублённого уточнения**. Пользователь уже понимает класс задачи; AI помогает соотнести конкретный объект с возможностями INDAI.

### 9.2 Разрешённое поведение

- Уточнять параметры объекта пользователя
- Объяснять, подходит ли данная услуга для описанного объекта
- Направлять к другой Service Page, если задача покрывается иной услугой
- Объяснять инженерную логику подхода глубже, чем контент страницы
- Сообщать об ограничениях применимости

### 9.3 Запрещённое поведение

- Инициировать диалог (pop-up, auto-open)
- Называть цены или диапазоны цен
- Запрашивать контактные данные
- Создавать urgency
- Дублировать контент страницы вместо углубления

### 9.4 Триггер

- Виджет статичен и видим
- Активируется только по клику пользователя
- Не перекрывает контент страницы

## 11. Критерии приёмки (QA / Review)

### 11.1 Автоматизируемые проверки

| # | Проверка | Метод |
|---|---|---|
| A1 | URL не содержит название метода, объекта или отрасли | Regex по sitemap |
| A2 | H1 не содержит: цифр, «%», «₽», «гарантия», «бесплатно», «лучший» | Regex / lint |
| A3 | Ни одна кнопка не содержит: «заказать», «купить», «получить цену», «оставить заявку» | Grep по DOM |
| A4 | Блоки идут в каноническом порядке (1–8, опционально 9) | Компонентный аудит |
| A5 | Отсутствуют формы захвата (input[type=tel], input[type=email] вне AI-виджета) | DOM-проверка |
| A6 | Schema.org не содержит `AggregateRating`, `Offer`, `Product` | Structured data validator |
| A7 | AI-виджет не вызывает auto-open при загрузке | E2E-тест |
| A8 | Порядок блоков mobile = desktop | Visual regression |
| A9 | Нет SEO-текстовых блоков вне шаблона | Контентный аудит |

### 11.2 Ручные проверки (review)

| # | Проверка | Критерий прохождения |
|---|---|---|
| M1 | **«Тест клининга»:** можно ли страницу без изменений разместить на сайте бытового клининга? | Если да → страница некорректна |
| M2 | **«Тест метода»:** страница называет метод в заголовке или URL? | Если да → нарушение §6.1 |
| M3 | **«Тест обещания»:** есть ли на странице конкретная цифра результата или слово «гарантия»? | Если да → нарушение §6.6 |
| M4 | **«Тест давления»:** есть ли элемент, ускоряющий пользователя к действию? | Если да → элемент удаляется |
| M5 | **«Тест самодостаточности»:** понятна ли страница без предварительного посещения HomePage? | Если нет → Блок 1 недостаточен |
| M6 | **«Тест шаблона»:** все ли обязательные блоки (1–8) присутствуют в каноническом порядке? | Если нет → нарушение §6.9 |
| M7 | **«Тест social proof»:** есть ли отзывы, логотипы клиентов, рейтинги? | Если да → нарушение §6.11 |

## 12. Процедура изменений (Addendum)

### 12.1 Что требует addendum

Любое изменение:

- состава канонических услуг (§4)

- правил SEO (§7)

```
ADDENDUM #[номер]
Дата: YYYY-MM-DD
Инициатор: [имя / роль]
Затрагивает: [номера секций данного документа]
Обоснование: [почему изменение необходимо]
Изменение: [точная формулировка]
Статус: DRAFT → REVIEW → APPROVED → LOCKED
```

- «SEO-специалист рекомендует»
