## 0. Роль документа в системе

Данный документ НЕ описывает философию Home Page.  
Он переводит архитектурный канон Home Page в **проверяемые правила реализации**.

Документ отвечает на вопрос:

> Как понять, что Home Page реализована правильно — в коде, дизайне и контенте?

Любой участник команды (разработчик, дизайнер, копирайтер, QA) должен быть способен  
**самостоятельно** определить корректность реализации, используя только этот документ.

## 2. Целевой пользователь Home Page

### 2.1 Целевой пользователь (должен пройти фильтр)

**Роль:** лицо, принимающее или влияющее на решения по обслуживанию промышленных объектов.

**Наблюдаемые индикаторы (для проектирования и тестирования):**

| Индикатор | Пример |
|---|---|
| Тип объекта в запросе | завод, котельная, НПЗ, энергоблок, теплообменник, резервуар, трубопровод |
| Характер задачи | накипь, отложения, коррозия, снижение КПД, нарушение теплообмена, подготовка к ревизии |
| Контекст принятия решений | тендер, плановый ремонт, аварийный простой, предписание Ростехнадзора |
| Язык запроса | инженерная терминология, ссылки на регламенты, упоминание параметров оборудования |
| Готовность к процессу | готов предоставить данные об объекте, понимает необходимость обследования |

### 2.2 Нецелевой пользователь (должен самостоятельно отсеяться)

**Наблюдаемые индикаторы:**

| Индикатор | Пример |
|---|---|
| Тип объекта | квартира, офис, автомобиль, фасад частного дома |
| Характер запроса | «сколько стоит помыть», «нужна уборка», «почистить кондиционер» |
| Ожидания | цена сразу, выезд сегодня, гарантия результата без обследования |
| Модель выбора | сравнение по цене, поиск скидок, эмоциональное решение |

**Принцип:** нецелевой пользователь должен уйти **без раздражения и без ощущения, что его оттолкнули**. Он просто должен понять: «это не тот масштаб задач, который мне нужен».

## 3. Функция Home Page (строго)

Home Page **НЕ продаёт** и **НЕ убеждает**.

Её единственные функции:

1. **Сформировать рамку применимости** — показать, с какими объектами и задачами работает INDAI.
2. **Показать инженерную природу** — передать, что это инженерный процесс, а не бытовая услуга.
3. **Отфильтровать нецелевых** — через контент, язык и структуру, не через запреты.
4. **Подготовить к следующему шагу** — Service Pages или инженерный диалог через AI-ассистента.

**Диагностический тест функции:**  
Если после просмотра Home Page пользователь думает «мне нужно сравнить цены» — функция нарушена.  
Если думает «мне нужно описать свой объект» — функция выполнена.

## 4. Секционная модель: операционные критерии

### 4.1 HERO

**Функция:** ориентация и первичная фильтрация.

**Корректная реализация:**

| Критерий | Проверка |
|---|---|
| H1 — утверждение о сфере, не оффер | H1 не содержит: цифр, сроков, слов «выгодно/быстро/дёшево/гарантия» |
| Подзаголовок — уточнение класса задач | Конкретизирует тип объектов или инженерных задач |
| Нет активного CTA | Отсутствует кнопка с формулировкой действия «получить/заказать/оставить» |
| AI-виджет не инициирует диалог | Виджет видим, но не открывает чат, не показывает prompt, не анимируется для привлечения внимания |
| Визуал — инженерный контекст | Изображение/фон — промышленный объект, оборудование, процесс. Не: улыбающиеся люди, абстрактные формы |

**Некорректная реализация (примеры):**

- «Экономия до 40% на обслуживании» — маркетинговый claim → запрещено
- «Получить бесплатную консультацию» — CTA захвата → запрещено
- HERO визуально неотличим от лендинга клининговой компании → запрещено

### 4.2 PROCESS

**Функция:** показать логику подхода INDAI, а не путь клиента к покупке.

| Разрешено | Запрещено |
|---|---|
| Этапы инженерного подхода (обследование → анализ → подбор метода → выполнение → верификация) | Этапы клиентского пути («оставьте заявку → мы перезвоним → назовём цену») |
| Формулировки «как мы подходим к задаче» | Формулировки «как это выгодно для вас» |
| Указание на необходимость данных об объекте | Обещания результата, KPI, ROI, проценты |
| Нейтральная визуализация этапов | Иконки «галочка/звезда/медаль», подразумевающие гарантию |

### 4.3 SERVICES

**Функция:** продуктовая навигация — показать, какие **классы задач** решает INDAI.

| Разрешено | Запрещено |
|---|---|
| Название услуги/направления | Цена, диапазон цен, «от X руб.» |
| Одна нейтральная фраза (до 15 слов), описывающая класс задачи | Описание выгод, преимуществ, результатов |
| Ссылка на Service Page | Превращение карточки в мини-лендинг |
| Иконка или изображение, соответствующее типу работ | Бейджи «хит», «популярно», «скидка» |

**Поведение при клике:** переход на соответствующую Service Page. Без модалок, без inline-раскрытия, без «узнать цену».

**Количество:** определяется Master Spec. Если не определено — запросить уточнение.

### 4.4 EFFECTS (опционально, если присутствует в секционной модели)

**Функция:** показать **типы инженерных эффектов**, а не результаты конкретных проектов.

| Допустимо | Запрещено |
|---|---|
| Категории эффектов: восстановление теплообмена, снятие отложений, подготовка поверхности | «Повысили КПД на 35%», «Сэкономили 2 млн руб.» |
| Типы задач: очистка от накипи, удаление коррозионных отложений | Фото «до/после» |
| Инженерные параметры как **категория**: «работа при давлении до 1500 бар» | Инженерные параметры как **обещание**: «гарантируем давление 1500 бар» |
| Перечисление типов объектов | Сравнения с конкурентами, отзывы, эмоциональные формулировки |

**Разграничение факт/обещание (эталонные примеры):**

| Формулировка | Тип | Допустимость |
|---|---|---|
| «Метод применим при температурах до 300°C» | Параметр категории | ✅ Допустимо |
| «Гарантируем работу при 300°C» | Обещание | ❌ Запрещено |
| «Гидродинамическая очистка — давление до 1500 бар» | Характеристика метода | ✅ Допустимо |
| «Очистим ваш объект давлением 1500 бар» | Обещание действия | ❌ Запрещено |
| «Применяется на объектах нефтегазового сектора» | Контекст применимости | ✅ Допустимо |
| «Лучшее решение для нефтегазового сектора» | Маркетинговый claim | ❌ Запрещено |

### 4.5 CTA / ВХОД В ДИАЛОГ

**Функция:** приглашение к проверке применимости, не захват лида.

**Допустимые формулировки:**

- «Обсудить задачу»
- «Описать объект»
- «Проверить применимость»
- «Задать инженерный вопрос»

**Запрещённые формулировки:**

- «Получить цену»
- «Заказать»
- «Оставить заявку»
- «Бесплатная консультация»
- «Рассчитать стоимость»
- «Получить коммерческое предложение»

**Операционный тест:** если формулировка CTA подходит для бытовой клининговой компании — она запрещена для INDAI.

**Расположение:** CTA допустим только после секций, формирующих контекст (PROCESS, SERVICES). Не допускается в HERO и не допускается в sticky/floating формате.

### 4.6 FOOTER

**Функция:** навигационная и юридическая.

| Разрешено | Запрещено |
|---|---|
| Навигация по разделам сайта | Дублирование CTA |
| Контактные данные (телефон, email, адрес) | Формы захвата |
| Юридическая информация | Маркетинговые слоганы |
| Ссылки на соцсети (нейтрально) | Счётчики, бейджи, «нам доверяют X компаний» |

### 4.7 Отсутствующие секции (явный запрет)

Следующие секции **запрещены** на Home Page, если не одобрены отдельным addendum:

| Секция | Причина запрета |
|---|---|
| «До / После» | Маркетинговый приём, нарушает принцип фильтрации |
| «Отзывы клиентов» | Social proof = инструмент убеждения |
| «Гарантии» | Обещание, не факт |
| «Калькулятор стоимости» | Подменяет инженерную валидацию |
| «Партнёры / Клиенты» (логотипы) | Trust-сигнал = маркетинг |
| «Акции / Скидки» | Прямое нарушение архитектуры |
| «FAQ на Home Page» | Риск подмены Service Pages |
| SEO-текстовые блоки | См. секцию 5 данного документа |

## 5. SEO и поисковая оптимизация на Home Page

### 5.1 Принцип

Home Page **не является SEO-инструментом**.

Задача поисковой видимости решается на уровне Service Pages, блога и отраслевых страниц.
Home Page обслуживает пользователя, который **уже пришёл** — а не поисковый алгоритм.

### 5.2 Запрещено на Home Page

| Элемент | Причина запрета |
|---|---|
| SEO-текстовые блоки («простыни» внизу страницы) | Не несут ценности для целевого пользователя; нарушают инженерный тон |
| Скрытый или свёрнутый текст для индексации | Манипуляция поисковиком; противоречит принципу прозрачности |
| Keyword stuffing в H1/H2/alt | Превращает инженерное утверждение в SEO-конструкцию |
| Блоки «Услуги в [город]» / «Очистка [объект] в [регион]» | Геоспам; не соответствует роли Home Page |
| Автогенерируемые тексты для наращивания объёма | Нарушают архитектурную дисциплину контента |
| Schema.org разметка типа `Product`, `Offer`, `AggregateRating` | Home Page — не товарная страница; допустимы только `Organization` и `WebSite` |

### 5.3 Допустимо

| Элемент | Условие |
|---|---|
| Корректный `<title>` и `<meta description>` | Формулировка соответствует архитектурной роли: описание сферы, не оффер |
| Семантическая HTML-разметка (h1–h3, section, article) | Естественная структура, не ради SEO |
| Schema.org: `Organization`, `WebSite` | Только эти типы |
| Open Graph / Twitter Card теги | Для корректного отображения при шеринге |
| Canonical URL | Стандартная техническая мера |

### 5.4 Принцип разграничения

> **Если элемент добавляется «для поисковика», а не для пользователя — он запрещён на Home Page.**

Тест: убрать элемент. Если целевой пользователь ничего не потерял — элемент был SEO-мусором.

### 5.5 Где решается SEO

| Задача | Где решается | Не на Home Page |
|---|---|---|
| Поисковая видимость по услугам | Service Pages | ✅ |
| Геотаргетинг | Отраслевые / региональные лендинги | ✅ |
| Длинный хвост запросов | Блог / Knowledge Base | ✅ |
| Бренд-запросы | Home Page (но без SEO-текстов) | Только title + meta |

## 6. Правило инженерных фактов

### 6.1 Категорически запрещено

- Маркетинговые метрики: «№1 в отрасли», «более 500 объектов»
- Обобщённые выгоды: «экономия до X%», «повышение эффективности»
- Универсальные цифры результата
- Сравнения с конкурентами (прямые или косвенные)

### 6.2 Допустимо (ограниченно)

- Характеристики метода как **категории**: давление, температура, тип среды
- Типы объектов и отраслей как **контекст применимости**
- Классификация задач без количественной оценки результата

### 6.3 Принцип разграничения

> **Факт о методе допустим. Обещание результата — нет.**

Тест: если формулировку можно использовать в инженерной документации (паспорт оборудования, ТУ, регламент) — допустимо. Если только в коммерческом предложении — запрещено.

## 7. AI-ассистент на Home Page

### 7.1 Роль

AI-ассистент на Home Page — это **инструмент уточнения применимости**, а не канал продаж.

### 7.2 Разрешённое поведение

- Уточнять тип объекта и задачи пользователя
- Определять, относится ли задача к зоне ответственности INDAI
- Направлять к соответствующей Service Page
- Объяснять инженерную логику подхода
- Сообщать, что задача не входит в сферу INDAI (корректный отказ)

### 7.3 Запрещённое поведение

- Инициировать диалог (pop-up, автооткрытие, анимированные подсказки)
- Называть цены или диапазоны цен
- Запрашивать контактные данные
- Создавать urgency («осталось 2 слота», «акция до конца недели»)
- Подменять собой контент страницы

### 7.4 Триггер появления

- Виджет **статичен и видим** с момента загрузки страницы
- Не анимируется, не мигает, не выезжает
- Активируется только по клику пользователя

### 7.5 Поведение при первом сообщении

При открытии виджета пользователь видит **нейтральное приглашение** (не вопрос, не оффер):

> Пример: «Опишите объект или задачу — я помогу определить применимость наших методов.»

### 7.6 Fallback при нецелевом запросе

Если AI определяет, что задача нецелевая:

- Сообщает корректно и без оценки
- Не предлагает «альтернативы»
- Не пытается удержать пользователя

> Пример: «Задачи этого типа не входят в нашу специализацию. Мы работаем с промышленными объектами и инженерными системами.»

## 8. Адаптивность (Mobile / Desktop)

### 8.1 Общее правило

Порядок секций и логика фильтрации **не должны нарушаться** при адаптации к мобильным устройствам.

### 8.2 Mobile-специфичные требования

| Требование | Обоснование |
|---|---|
| Порядок секций идентичен desktop | Фильтрационная последовательность не должна ломаться |
| AI-виджет не перекрывает контент | Пользователь сначала читает, потом решает обратиться |
| CTA не становится sticky/floating | Запрет на давление усиливается на mobile |
| H1 полностью виден без скролла | Первичная ориентация — приоритет |

## 9. Мультиязычность

### 9.1 Поддерживаемые языки

| Язык | Статус | Приоритет |
|---|---|---|
| Русский | Основной | Первичная реализация |
| Английский | Вторичный | Определяется Master Spec |

### 9.2 Правила локализации

- Перевод **не меняет** архитектурную роль секций
- Все канонические запреты действуют **в любой языковой версии**
- Формулировки CTA переводятся с сохранением нейтрального тона (не адаптируются «под рынок»)
- Переключатель языка — в header, без акцента

## 10. Критерии приёмки (QA / Review)

### 10.1 Автоматизируемые проверки

| # | Проверка | Метод |
|---|---|---|
| A1 | H1 не содержит цифр, «%», «₽», «от», «до», «гарантия», «бесплатно» | Regex / lint |
| A2 | Ни одна кнопка не содержит: «заказать», «купить», «получить цену», «оставить заявку» | Grep по DOM |
| A3 | Отсутствуют секции из списка 4.7 (запрещённые) | Компонентный аудит |
| A4 | AI-виджет не вызывает auto-open при загрузке | E2E-тест |
| A5 | Порядок секций mobile = desktop | Visual regression |
| A6 | CTA отсутствует выше секции PROCESS | DOM-порядок |
| A7 | Отсутствуют SEO-текстовые блоки (>200 слов подряд без структурной роли) | Контентный аудит |
| A8 | Schema.org содержит только `Organization` и/или `WebSite` | Проверка structured data |
| A9 | `<title>` и `<meta description>` не содержат keyword stuffing | Ручной + regex |

### 10.2 Ручные проверки (review)

| # | Проверка | Критерий прохождения |
|---|---|---|
| M1 | «Тест клининга»: можно ли карточку услуги без изменений поставить на сайт бытового клининга? | Если да → карточка некорректна |
| M2 | «Тест лендинга»: можно ли HERO-блок спутать с рекламным лендингом? | Если да → HERO некорректен |
| M3 | «Тест давления»: есть ли на странице элемент, ускоряющий пользователя к действию? | Если да → элемент удаляется |
| M4 | «Тест автономности»: работает ли страница без AI-виджета? | Если нет → зависимость от AI-виджета → ошибка |
| M5 | «Тест нецелевого»: может ли частное лицо подумать, что INDAI подходит для его квартиры? | Если да → фильтрация не работает |

## 11. Процедура изменений (Addendum)

### 11.1 Что требует addendum

Любое изменение:

- роли или функции секции
- состава секций (добавление / удаление)
- формулировок CTA
- поведения AI-ассистента
- критериев приёмки

### 11.2 Формат addendum

```
ADDENDUM #[номер]
Дата: YYYY-MM-DD
Инициатор: [имя / роль]
Затрагивает: [номера секций данного документа]
Обоснование: [почему изменение необходимо]
Изменение: [точная формулировка]
Статус: DRAFT → REVIEW → APPROVED → LOCKED
```

### 11.3 Запрещённые основания для addendum

Следующие аргументы **не являются** допустимым обоснованием:

- «конверсия вырастет»
- «рынок так делает»
- «конкуренты так делают»
- «дизайнер предложил»
- «клиент просит кнопку»
- «сроки поджимают»
